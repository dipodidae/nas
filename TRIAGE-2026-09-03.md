## P1 — autoheal, exit 139

### Reported

> autoheal is dead, exit 139 (SIGSEGV), down since 09-02 19:40. Nothing is
> restarting unhealthy containers.

### Actual state: running, and demonstrably working

```
$ docker compose ps
autoheal   autoheal   running   Up 18 hours
```

Not just running — actually supervising. A throwaway canary carrying
`autoheal=true` and a permanently-failing healthcheck was created, and autoheal
picked it up on its own:

```
$ docker logs autoheal --since 8m
03-09-2026 12:53:07 Container /canary-unhealthy (5c3569a6d4ee) found to be unhealthy - Restarting container now with 150s timeout
03-09-2026 12:56:07 Container /canary-unhealthy (5c3569a6d4ee) found to be unhealthy - Restarting container now with 150s timeout

$ docker inspect canary-unhealthy --format '{{.State.StartedAt}}'
2026-09-03T12:52:31Z   ->   2026-09-03T12:55:37Z   (moved by autoheal's restart)
```

The restart path through `dockerproxy` was confirmed independently, which matters
because the proxy is narrowed and `ALLOW_RESTARTS=0`:

```
$ curl -X POST http://dockerproxy:2375/containers/canary-unhealthy/restart?t=5
restart_http=204
```

`CONTAINERS=1` + `POST=1` is sufficient; `ALLOW_RESTARTS` is not consulted for
this path in the running proxy version. The canary was removed afterwards.

### The exit 139 was real, happened once, and left no kernel trace

The watchdog did observe it:

```
$ grep -A2 '2026-09-02T19:40:01' logs/stack_watchdog.log
[CRITICAL] container:autoheal:down: autoheal: exited, exit=139
[CRITICAL] autoheal:down: autoheal is not running — nothing is restarting unhealthy containers
```

But the kernel recorded no segfault at all, anywhere in the boot that contains
the event:

```
$ journalctl --list-boots
  0 5fda08c91ef148fb8ea802212a17384b  Wed 2026-09-02 13:52:45 CEST  Thu 2026-09-03 14:49:38 CEST

$ journalctl -k --no-pager | grep -ci segfault
0
```

The event (≈19:38 CEST on 09-02) is **inside** boot 0, so the record would still
be present if the kernel had made one. `show_unhandled_signals` is on by default
on x86-64, so a userspace SIGSEGV normally produces a `segfault at … ip …` line.
Its total absence is evidence against the `ld-musl` crash class, though not
absolute proof — a process that installs its own SIGSEGV handler and exits, or
one killed by an explicit `SIGSEGV`, would also produce exit 139 with no kernel
line.

Nothing else supports a local cause either:

- `OOMKilled=false`, and no `oom-kill` lines in the kernel log.
- No memory limit on the service (Pi-era caps were removed, ADR-0001).
- Watchtower is retired (ADR-0025) and `diun` has no route to the Docker API, so
  no recreate could have raced the loop. `diun`'s first manifest run at
  09-02 19:39:56 is ~2 min before the exit, but `diun` is a file-provider
  notifier with no Docker socket — correlation only.
- `read_only: true` + `tmpfs: /tmp` is unusual for a shell-and-curl image and is
  the most plausible local irritant, but it has since run 18 h unchanged under
  exactly that config, so it is not sufficient on its own.

**Inconclusive, stated plainly:** with one occurrence, no kernel line, and no
core dump configured, the cause of the single exit 139 cannot be established from
what is on the box. It is not currently recurring.

### Why it still looks down: see [F1](#f1-resolve-notifications-are-silently-consumed)

`ExitCode=0` and `FinishedAt=2026-09-02T17:45:43Z` (19:45:43 CEST) with
`StartedAt=2026-09-02T18:19:16Z` (20:19:16 CEST) and `RestartCount=0` describe
what happened after the crash: it was brought up, stopped cleanly at 19:45:43,
and cold-started at 20:19:16. (`RestartCount` resets on a manual `docker start`,
so 0 does not contradict the crash.) The clean stop at 19:45 is consistent with
the ADR-0026 lever — stopping autoheal by hand is the only way to stop it
restarting slskd, because labels are immutable.

### The actual damage in that window was autoheal restarting slskd

This is the finding worth keeping from P1. autoheal's own log for 09-02:

```
02-09-2026 12:01:02 Container /slskd (6db373a71ab5) found to be unhealthy - Restarting container now with 150s timeout
02-09-2026 12:07:50 ... 12:16:51 ... 12:25:52 ... 12:34:52 ... 12:43:53 ... 12:52:53
02-09-2026 13:01:54 ... 13:10:55 ... 13:19:55 ... 13:28:56 ... 13:37:56 ... 13:46:57
02-09-2026 13:55:58 ... 14:04:58 ... 14:13:59 ... 14:22:59 ... 14:32:00 ... 14:41:01

```

24 restarts of slskd in ~4¼ hours, every ~9 minutes. Each restart mid-scan marks
the share scan suspect, which forces a full rescan on the next start — the

Those restarts are the origin of the 27 slskd flap alerts in [P3](#p3--slskd-unhealthy),

`autoheal` also has **no healthcheck at all** (`healthcheck: disable: true` in
`compose/infra.yaml`; `docker inspect` → `NO-HEALTHCHECK`), so a hung-but-running
autoheal is invisible to Docker. `stack_watchdog.check_autoheal()` covers

### Fix

| Fix | Status |
|---|---|
| Guard the watchdog's state write so ad-hoc runs stop eating resolves ([F1](#f1-resolve-notifications-are-silently-consumed)) | **done** (`101b852`) |
| Give `autoheal` a real healthcheck | **done** (`a94aca5`) |
| Replace `autoheal` with `qmcgaw/deunhealth` | **declined** — autoheal kept |

The swap was declined on the evidence: no kernel segfault anywhere in the boot
containing the event, no local cause found, 19 h stable, and `deunhealth`'s only
semver tag is v0.3.0 from 2021 while `latest` was rebuilt 2025-12-22 — so "pin a
tag" and "use a maintained build" cannot both hold.

The healthcheck turned up its own finding. The image ships
`pgrep -f autoheal || exit 1`, which **can never fail**: `pgrep -f` matches the
probe's own shell, because the pattern is in its command line.

```
$ docker exec autoheal sh -c 'pgrep -f autoheal'
1        <- sh /docker-entrypoint autoheal
13537    <- sh -c pgrep -f autoheal
```

That is why it was `disable: true`. The replacement asserts the failure mode
autoheal actually has — that it can reach the Docker API at all — since a
running, correctly-labelled autoheal that cannot reach `dockerproxy` supervises
nothing and looks fine from outside.

On the swap: `deunhealth` reads `DOCKER_HOST` and accepts `tcp://dockerproxy:2375`,
so it *can* preserve the invariant that `dockerproxy` is the only container
touching `/var/run/docker.sock` — but only by giving up `network_mode: none`,
since it then needs `nas-network` to reach the proxy. It also exposes a health
server on `127.0.0.1:9999`, which is a better watchdog target than autoheal's
nothing. The pinning advice does not survive contact with the registry, though:
the newest semver tag is **v0.3.0 from 2021-10-17**, while `latest` was rebuilt
2025-12-22. "Pin a tag, not latest" and "use a maintained build" are in direct
conflict here, which is the crux of the decision.

## P2 — cron `playlist-sync` has never succeeded

The report is correct that it has never succeeded, and correct that the alerting
is wrong. It is not correct that this is a 43-hour-old config bug. There are
**three** separate causes.

### Cause 1 — a run from yesterday is still in flight and holds the lock

```
$ ps -eo pid,etime,cmd | grep cron-sync
365854  20:35:24  /bin/sh -c /usr/bin/flock -n /tmp/nas-playlist-sync.lock ... --name playlist-sync ...
365905  20:35:24  bash /home/tom/nas/webapps/jellyfin-playlist-generator/cron-sync.sh
366042  20:35:24  docker exec playlist-generator curl -sf -N -X POST http://127.0.0.1:8000/sync/full-pipeline?skip_audio=false

$ flock -n /tmp/nas-playlist-sync.lock -c 'echo free'
LOCK IS HELD
$ fuser -v /tmp/nas-playlist-sync.lock
tom  365860  flock
tom  365862  python
```

The run started 09-02 18:10 and is still going. Consequences:

- `flock -n` made the 00:10, 06:10 and 12:10 ticks **silent no-ops**. This is the
  exact trap the crontab header warns about, and the wrapper being inside the
  lock is what stops it being mis-recorded as success. It also means the only
  possible signal is the `:stale` alert — which is what fired.
- `cron_job.py:141` uses `subprocess.run(..., capture_output=True)`, which
  buffers everything until the child exits, so `logs/playlist_sync.log` has not
  been written since 09-02 13:50 despite 21 h of work. The job looks dead in the
  log while running fine.
- `state["last_success"]` is only written after the child exits
  (`cron_job.py:229`), so a long run cannot refresh the freshness clock while it
  is in flight.

And the run *is* working — it is not wedged:

```
$ docker logs playlist-generator --tail 5
2026-09-03 14:56:31,817 - httpx2 - INFO - HTTP Request: POST https://ws.audioscrobbler.com/2.0/ "HTTP/1.1 200 OK"
2026-09-03 14:56:32,177 - pylast - INFO - track.getInfo
```

(`/scan/status` reports `is_running: false, status: idle` throughout — the
full-pipeline endpoint does not update the scan tracker for enrichment stages, so
that endpoint is misleading here and should not be used to judge liveness.)

### Cause 2 — the work does not fit the window, by two orders of magnitude

Measured from the backend's own progress lines today:

```
11:06:39  Enriching 10500/144756 tracks (saved to DB)
14:44:36  Enriching 17400/144756 tracks (saved to DB)
```

6,900 tracks in 3 h 38 min ≈ **1,900 tracks/h**. The remaining 127,356 tracks
need **≈ 67 hours** for the Last.fm track stage alone, before Metal Archives,
embeddings, profiles, clustering, audio and search vectors.

The cron line is `10 */6 * * *` with `--max-age-min 1440`. A job needing ~3+ days
per pass, scheduled every 6 h, judged stale after 24 h, cannot ever report
success. That is a scheduling-model error, not a broken credential.

It is also long-standing rather than new. `logs/playlist_sync.log` records the
same ending going back weeks:

```
2026-08-24 11:06:02 [ERR]   Pipeline did not complete cleanly. Stamp left unchanged (will retry).
2026-08-26 21:02:01 [ERR]   ...
2026-08-29 18:59:00 [ERR]   ...
2026-09-01 05:02:31 [ERR]   ...
2026-09-01 18:29:41 [ERR]   ...
2026-09-02 10:50:33 [ERR]   ...
2026-09-02 13:50:42 [ERR]   ...
--- playlist-sync exit=1 in 38432.4s      # one run lasted 10.7 hours
```

`"registered": 1788284541` = 09-01 19:42:21 CEST is when `logs/cron-state/` was
created and the wrapper adopted the job — **not** when the job was added. The
"registered ~43h ago" reading is an artifact of that.

Each ending is `Stream closed without a completion signal.`, i.e. the SSE stream
from `/sync/full-pipeline` ended with no `done` event (`cron-sync.sh`, the
`if not got_done` branch → exit 2 → wrapper exit 1). The durations are wildly
different (100 min, 10.7 h, and the current 21 h and counting) and the stage at
death varies, so this is not a fixed timeout. Holding a single HTTP stream open
for multiple days is the design problem underneath; the specific close cause for
any past run is **not recoverable** — the backend container was restarted
09-02 17:21:08 CEST, so those logs are gone, and the current run has not closed.

### Cause 3 — the alerting cannot distinguish "broken" from "still working"

`check_cron_jobs()` (`stack_watchdog.py:290`) measures from
`state["last_success"] or state["registered"]`. With no success ever recorded,
the reference is the registration time, so it went stale at
09-01 19:42 + 24 h = 09-02 19:42, and the first `*/5` tick after that fired:

```
$ cat logs/stack_watchdog.json
"cron:playlist-sync:stale": { "first_seen": 1788371102, "last_notified": 1788438902 }
                                          = 09-02 19:45:02        = 09-03 14:35:02
```

Then `--repeat-min 60` re-pushed it hourly, forever: **20 identical `p5` messages**
in the window per ntfy's cache. The code already tells the two cases apart in the
*message* —

```python
what = f"has never succeeded (registered {age_min / 60:.1f}h ago)"
```

— but not in the *cadence*, even though `Alert.repeat_min` exists precisely for
"not all alerts are the same kind of thing" and is unused here.

### Cause 4 (adjacent, separately provable) — MusicBrainz album resolution has never once worked

Not a cause of the exit 1, but found while tracing it, and worth its own line
because it silently voids a whole enrichment stage:

```
$ docker logs playlist-generator --since 24h | grep ' - WARNING - '
MB album resolution error for 'Zenyattà Mondatta': value too long for type character varying(10)
MB album resolution error for 'Yer’ Album': value too long for type character varying(10)
```

```
$ psql -c '\d mb_lookup_cache'

$ psql -c 'select entity_type, count(*) from mb_lookup_cache group by 1'
 artist | 3143          <- 6 chars, fits

$ psql -c 'select count(*) from albums where musicbrainz_id is not null'
```

The literal is 13 characters:

```
service/app/ingestion/musicbrainz.py:370   VALUES ('release_group', %s, %s, %s)

service/app/database_pg.py:464             entity_type  VARCHAR(10) NOT NULL,
```

`'release_group'` (13) into `VARCHAR(10)` throws on every album, in both the
match and the no-match branch; the `except Exception` at `musicbrainz.py:531`
swallows it as a WARNING, and `stats["albums_resolved"] += 1` on the line after

resolution has never produced a single row.

The fix is one word (`VARCHAR(10)` → `VARCHAR(32)`) plus an `ALTER TABLE` on the
live database. Both land **outside this repo**:
`webapps/jellyfin-playlist-generator` is a submodule of
`dipodidae/jellyfin-playlist-generator` (currently `27cb8d9`, branch `main`,
clean). Listed as a blocker rather than done.

### What replaced it

`scripts/playlist_sync_stage.py` runs one stage per invocation, bounded. Two
things made this far cheaper than expected, and both were measured rather than
assumed:

**Every stage already had its own endpoint** — no submodule change was needed
for the split at all. But the plain `POST /enrich/<stage>` endpoints are
**fire-and-forget**:

```
$ docker exec playlist-generator curl -sf -X POST '.../enrich/release-dates?max_albums=1'
{"status":"started","message":"Release date resolution started in background"}
```

A cron job calling those would exit 0 having verified nothing. Only the
`/stream` variants block and emit a terminal `done` event, and a *bounded*
stream is short — which is the actual fix. The failure was never SSE as such; it
was a three-day SSE.

**Only the I/O-bound stages can be scheduled.** The backend is a single uvicorn
worker, and the distinction is sharp:

| | Behaviour | Evidence |
|---|---|---|
| `lastfm-*`, `release-dates` | await on HTTP, event loop stays free | playlist-generator stayed **healthy** through the 22 h Last.fm run |
| `embeddings`, `profiles`, `clusters`, `banger-flags`, `genre-manifold`, `audio` | peg a core inside the request handler, block `/health` | one `banger-flags` run → `unhealthy streak=23` at `CPU=101.63%` |

I found the second one the hard way: a `banger-flags` test run took the container
unhealthy and **paged at 15:35** (`container:playlist-generator:unhealthy`,
streak 5). Recovered by recreating the container — the work is derived and
recomputable. That is why only the three I/O-bound stages are in the crontab and
the CPU-bound ones stay manual.

Installed (all sharing `/tmp/nas-playlist-stage.lock`):

```
*/30  playlist-lastfm-tracks     --stage lastfm-tracks     --limit 300   --max-age-min 180
:12   playlist-album-tags        --stage lastfm-album-tags --limit 300   --max-age-min 300
:42   playlist-release-dates     --stage release-dates     --limit 300   --max-age-min 300
```

The batch is sized off the **slower** of two measured rates: ~1,900 tracks/h in
the long run, but a fresh 20-track batch took 93.7 s (~770/h), so per-run
overhead is real. An overrun just makes `flock -n` skip a tick.

Verified live:

```
OK: release-dates completed (albums_processed=5, albums_resolved=4, ..., errors=0)
--- playlist-release-dates exit=0 in 14.8s
OK: lastfm-tracks completed (stats_added=20, tags_added=0, tracks_processed=20)
--- playlist-lastfm-tracks exit=0 in 93.7s
```

The availability gate was exercised too — with the backend wedged it reported
`exit 1` and did **not** page.

The 21.5 h in-flight run was stopped at 18,100/144,756 tracks; Last.fm progress
is written per batch (`saved to DB`), so the drip resumes from there rather than
restarting. Its `cron:playlist-sync:failed` alert was resolved by hand, because
a retired job can never close its own — the "open alert that cannot close"
problem `cron_job.py`'s own docstring warns about.

**Still open:** the six CPU-bound stages have no schedule. They need the backend
to run them off the event loop (a worker, or `--workers > 1`) before they can be
automated. Until then: `python scripts/playlist_sync_stage.py --stage <name>`,
knowing it will take the container unhealthy for the duration.

## P3 — slskd unhealthy

### Actual state: healthy, and logged in

```
$ docker inspect slskd --format '{{json .State.Health}}' | jq '{Status, FailingStreak}'
{ "Status": "healthy", "FailingStreak": 0 }
{"Start":"2026-09-03T14:45:26+02:00","ExitCode":0,"Output":"URL: http://localhost:5030/ 200 OK"}
```

### Neither of the suspected healthcheck bugs applies

The healthcheck is **exec form**, and the binary it invokes exists and works —
the probe output above is `wget`'s own. Not the missing-binary class of
slskd/slskd#99, and not a `CMD-SHELL` swallowing failure:

```
$ docker inspect slskd --format '{{json .Config.Healthcheck.Test}}'
["CMD","wget","--no-verbose","--tries=1","--spider","http://localhost:5030/"]
```

`/api/v0/server` is also **correct**, not wrong. slskd is `0.26.0.0+e42a525d` and
the endpoint answers with the login state the script parses:

```
$ tail logs/slskd_login_watch.log
--- slskd-login-watch start 2026-09-03T14:45:01+0200
OK: slskd logged in (state=Connected, LoggedIn)
--- slskd-login-watch exit=0 in 0.1s
```

That has been the result on every 15-minute tick today. `scripts/slskd_login_watch.py`
needs no change. Its earlier `exit 2` was `slskd_state.unreachable_exit_code()`
correctly reporting that slskd had **no HTTP listener at all** — slskd does not
bind `:5030` until its share scan completes.

There is also no gluetun in the path to confuse `localhost:5030`: the WireGuard
sidecar was removed 2026-07-27, slskd is a plain `nas-network` member publishing
`127.0.0.1:5030:5030`, and the cron jobs run **on the host**, not in a container.

### Root cause: live config drift on the start_period

`compose/media-download.yaml:239` declares `start_period: 4h`. The running
container does not have it:

```
$ docker inspect slskd --format '{{.Config.Healthcheck.StartPeriod}}'
5400000000000        # nanoseconds = 5400 s = 90 minutes
```

```
$ docker compose config --hash='*'   vs   container config-hash label
slskd                    **DRIFTED**
```

The arithmetic then closes exactly. The container started 09-02 18:24:48 CEST,
so a 90-minute window ended **19:54:48**. `interval: 60s`, and the alert fired
five minutes later at streak 6:

```
$ grep -A3 '2026-09-02T20:00:01' logs/stack_watchdog.log
[WARNING] container:slskd:unhealthy: slskd: healthcheck failing (streak 6)
```

The scan running at the time was the forced full rescan the compose comment
records — 19,433 directories / 194,358 files / 113 min — which finishes around
20:17, after the 90-minute window had already expired. The comment block in
`compose/media-download.yaml` describes this precise event and the 4 h value that
was written to fix it; **the container was never recreated, so the fix is not
live.** The next cold scan would repeat it.

The `slskd-login-watch` and `lidarr-backlog-drip` cron jobs that "failed and
recovered together" share exactly this dependency — both exit 2 while slskd has
no listener, both cleared at 20:15 when it bound:

```
$ grep -A6 '2026-09-02T20:15:02' logs/stack_watchdog.log
[RESOLVED] cron:lidarr-backlog-drip:stale (was active 330 min)
[RESOLVED] cron:slskd-login-watch:stale (was active 325 min)
```

| Fix | Status |
|---|---|
| Recreate `slskd` so the declared `4h` start_period goes live | **done** |

## F1. Resolve notifications are silently consumed

The one new defect, and the reason this report's premises were stale.

`stack_watchdog.py` writes its state file unconditionally at the end of `main()`:

```python
save_state(
    args.state,
    {"active": still, "restart_counts": restarts, "oom_cursor": oom_cursor},
)
```

There is no `args.dry_run` guard. So **any** ad-hoc invocation — including
`--dry-run`, which exists specifically to change nothing — loads `active`,
computes that a problem is over, prints `[RESOLVED]` to its own stdout, skips the
notification, and then *persists the pruned state*. The pending resolve is
consumed. The next cron run has nothing left to announce, so the recovery is
never delivered and the alert stays open forever on the phone.

The signature is visible across the 09-02 20:15 → 20:20 boundary. At 20:15 three
alerts are active:

```
--- stack-watchdog start 2026-09-02T20:15:02+0200
[CRITICAL] container:autoheal:down: autoheal: exited, exit=139
[WARNING]  container:slskd:unhealthy: slskd: healthcheck failing (streak 21)
[CRITICAL] autoheal:down: autoheal is not running — ...
[RESOLVED] cron:lidarr-backlog-drip:stale (was active 330 min)
[RESOLVED] cron:slskd-login-watch:stale (was active 325 min)
```

At the very next tick all three are gone — with **no `[RESOLVED]` line for any of
them**:

```
--- stack-watchdog start 2026-09-02T20:20:01+0200
[CRITICAL] cron:playlist-sync:stale: cron job playlist-sync has never succeeded ...
```

and ntfy confirms nothing was delivered: 14 `container:slskd:unhealthy` messages
against 13 `RESOLVED:` ones, and no `RESOLVED: autoheal:down` after 19:40. The
resolve loop cannot have been skipped by the cron run itself — it iterates
whatever `active` holds — so `active` had already been pruned by something
between 20:15:02 and 20:20:01.

**Inconclusive:** an ad-hoc `--dry-run` between those ticks fits the signature
exactly, but ad-hoc runs leave no trace (the log only receives `cron_job.py`-wrapped
runs), so *that* it was pruned is proven while *what pruned it* is not. The
unguarded write is the mechanism that makes it possible either way, and it is
worth fixing on its own merits: a `--dry-run` that mutates shared state is a bug
regardless of who ran it.

Fix: **applied** — `save_state` is skipped under `--dry-run`.

## Blockers

### 1. byparr-proxy for 1337x — approved on a premise that turned out to be wrong

This was approved on my description of it, and my description was wrong in three
ways that all cut the same direction. It is **not** built. Re-decide with the
real facts:

- **There is no published image.** `docker manifest inspect
  ghcr.io/guyg2232/byparr-proxy:latest` → `denied`; the Docker Hub name does not
  exist either. Upstream ships a `Dockerfile` and expects `build: ./byparr-proxy`.
  So "pin a tag, not latest" — the thing you asked for on the watchdog — is
  **impossible here**. It would mean vendoring or submoduling third-party source
  into this repo and building it locally.
- **It is per-indexer, not a general Cloudflare passthrough.** `UPSTREAM` is a
  single base URL baked into the container (`UPSTREAM: https://1337x.to`). It
  would not help Uindex without a second instance. I implied otherwise.
- **It needs a custom Cardigann definition, not a proxy repoint.** Upstream's
  instructions are: copy `definitions/1337x-byparr.yml` into Prowlarr's
  `/config/Definitions/Custom/`, restart Prowlarr, add a *new* indexer
  "1337x (via Byparr)" pointing at `http://byparr-proxy:8888/`, and give it **no**
  FlareSolverr tag. So it is a new indexer definition plus a new container, not a
  change to the existing `Byparr` proxy entry.

Also: 48 stars, no licence stated in the README, single maintainer. Given that
this sits in the indexer path, and that "unpinnable + unlicensed + vendored" is
the opposite of how the rest of this repo treats third-party code, I did not
want to build it on an approval you gave for something cheaper than it is.
