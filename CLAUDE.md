# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

Single-host homelab NAS stack: **one** Compose project split across many files (`compose.yaml` + `compose/*.yaml` + `webapps/*/compose.yaml`, wired with the `include:` top-level element — see `docs/decisions/0000-compose-layout.md`) orchestrates SWAG (reverse proxy + Let's Encrypt), the \*arr suite (Sonarr/Radarr/Lidarr/Bazarr/Prowlarr), qBittorrent (with `qui` as its web UI), slskd, Jellyfin, Jellyseerr, Nextcloud, and Flaresolverr, plus a Vite landing page (`rootpage/`) and Python operations scripts (`scripts/`).

## Authoritative docs — read these first

- `AGENTS.md` — full conventions (Python style, shell style, Docker Compose rules, env var contract, exit codes). Treat as binding.
- `docs/decisions/` — 26 ADRs holding the incident history that used to live as inline comments in `docker-compose.yml`. The compose files now carry only a one-line `INVARIANT:` plus an ADR pointer. **If a line says `INVARIANT:`, read the ADR before changing it.** Start at `docs/decisions/README.md`.
- `.github/copilot-instructions.md` — short-form version of the same rules.
- `README.md` — service table, ports, setup walkthrough.
- `scripts/README.md` — per-script flags, exit codes, and the operational workflows (backup, audit, log prune, post-update verify, qBittorrent kickstart, Prowlarr priority management).

The root-level `*-README.md` / `OPTIMIZATION-*.md` / `RADARR_NAMING_*.md` / `JELLYFIN-NO-TRANSCODING-*.md` files document one-off historical fixes and tuning work. They are reference material, not active runbooks — don't assume their advice is still current without checking the live config.

## Common commands

Most tooling is wrapped in `package.json` scripts; prefer those over raw commands.

```bash
# Compose invariants + validation — run BOTH after any compose change
make check             # scripts/check-invariants.sh: 40 incident-derived assertions
make lint              # docker compose config -q (matches CI)

# Stack lifecycle
pnpm up | pnpm down | pnpm restart | pnpm logs | pnpm update
make bootstrap         # one-time: create nas-network, pre-chown qui + ntfy config dirs

# Applying an update is ALWAYS by hand — nothing in the stack does it
# (docs/decisions/0025-watchtower-retired.md). `diun` only notifies.
make pull-jellyfin              # pull + up -d + wait for healthy
make update-qbittorrent         # prompts to bump the pinned tag first
make measure-qbittorrent-stop   # re-measure the graceful stop (6.2s @ 128 torrents)
make submodules                 # ongehoord + jellyfin-playlist-generator
make install-hooks              # pre-commit hook running `make check`

# JS/TS lint (rootpage + repo)
pnpm lint              # check
pnpm lint:fix          # autofix

# Python (scripts/ — venv at .venv)
pnpm py:venv           # one-time: create .venv and install requirements
pnpm py:deps           # refresh deps in existing venv
pnpm py:lint           # ruff check scripts
pnpm scripts:test      # legacy import/env smoke harness (scripts/test_scripts.py)

# Pytest (unit tests in scripts/tests/) — no pnpm wrapper, run directly
. .venv/bin/activate && pytest -q scripts/tests
. .venv/bin/activate && pytest scripts/tests/test_backup.py::test_create_backup_success

# Compose validation (matches CI)
docker compose config > /dev/null

# Landing page (rootpage/ is its own pnpm workspace)
cd rootpage && pnpm install && pnpm run build   # outputs dist/, bind-mounted into SWAG
```

CI (`.github/workflows/ci.yml`) runs three gates: `docker compose config`, `pnpm lint`, and `ruff check scripts` + `python scripts/test_scripts.py` + `pytest -q scripts/tests` across Python 3.11/3.12/3.13. Match this locally before pushing.

## Architecture essentials

**One bridge network, one reverse proxy.** All services join `nas-network` (172.30.0.0/24). SWAG terminates TLS on `:80`/`:443`. **What publishes a service on its subdomain is the presence of `swag/proxy-confs/<service>.subdomain.conf`, bind-mounted read-only into SWAG — not the `swag=enable` label.** The linuxserver auto-proxy mod is _not_ installed here (no `DOCKER_MODS` is set), so the label is documentation and the conf is mechanism; `make check` asserts the two agree in both directions, because both had drifted (ADR-0022). Internal WebUIs bind to `127.0.0.1:<port>` only; the public surface is SWAG plus the P2P ports for slskd (50300) and qBittorrent (6881) and Jellyfin's LAN ports (8096/8920/7359/1900).

**No VPN — P2P runs on the home IP.** `slskd` and `qbittorrent` are plain `nas-network` members that egress over the host's home IP directly; Lidarr/Sonarr/SWAG/qui resolve `qbittorrent:8080` / `slskd:5030` as normal service DNS. Each publishes its own ports: qBittorrent `6881/tcp+udp` (BitTorrent, default) and `127.0.0.1:8080` (WebUI); slskd `50300/tcp` (Soulseek, default) and `127.0.0.1:5030` (WebUI). Inbound P2P requires forwarding `6881` and `50300` on the router — there is no VPN remote-port-forward doing it. The gluetun WireGuard sidecar (AirVPN) that used to tunnel both services was **removed** on 2026-07-27 (`vpn-configs/` + `WIREGUARD_*`/`AIRVPN_*` in `.env` deleted with it). Historical caveat if Soulseek logins start timing out: slskd on the home IP is what got the IP soft-blocked by slsknet before — the tunnel was originally introduced for exactly that. **Prowlarr** was never tunneled and is unaffected; its CF-protected indexers still route through `byparr` (FlareSolverr-compatible) tagged `cloudflare`.

**Two persistence roots, both env-driven.** Every service config lives at `${CONFIG_DIRECTORY}/<service>`; media and downloads live under `${SHARE_DIRECTORY}` with lowercase subfolders (`movies/`, `series/`, `music/`, `downloads/`, `books/`, `nextcloud-data/`). Never hard-code paths — the compose file is intentionally portable across hosts. On this host (Minisforum MS01) `SHARE_DIRECTORY=/mnt/drive` is an ext4 mount.

**Service dependency chain (compose `depends_on`):** prowlarr ← {sonarr, radarr, lidarr, bazarr}; qbittorrent ← {sonarr, radarr, lidarr, prowlarr}; slskd ← lidarr; jellyfin + sonarr + radarr ← jellyseerr; swag ← nextcloud. Lidarr is pinned to the `:nightly` tag; everything else uses `:latest` from `lscr.io/linuxserver/*` except slskd (no LSIO image — uses `slskd/slskd:latest` running as `${PUID}:${PGID}`), flaresolverr (ghcr.io), and jellyseerr (ghcr.io).

**Hardening pattern (apply to any new service):** `security_opt: no-new-privileges:true`, `cap_drop: ALL`, selective `cap_add` (typically `CHOWN`, `SETUID`, `SETGID`, `DAC_OVERRIDE`), bind WebUI to `127.0.0.1`, include a `curl -f` or `wget --spider` healthcheck, and cap container logs (`json-file` with `max-size: 10m`, `max-file: "2"`). Pi-era resource limits (`mem_limit`, `cpus`, `blkio_config`, `ulimit`) were removed for the MS01 host — do not reintroduce them without reason (`docs/decisions/0001-hardening-baseline.md`). Most of this shape is inherited rather than restated: services `extends` a fragment from `compose/_fragments.yaml` (`svc-base` → `svc-hardened` → `svc-hardened-tz` → `svc-lsio-env` → `svc-lsio` → `svc-arr`). **Run `make check` after any compose change** — `scripts/check-invariants.sh` asserts all of the above plus a dozen incident-derived rules, naming the ADR on failure.

**Scripts are operational, not deployed.** Nothing in `scripts/` runs inside containers; they are Python/Bash utilities executed from the host venv against the live services' HTTP APIs (using `API_KEY_*` env vars from `.env`) or directly against the filesystem. They share a small contract documented in `AGENTS.md`: exit `0` success / `1` partial / `2` fatal; side effects centralized in `main()`; pure logic elsewhere for testability.

## Repo-specific gotchas

- **Do not modify Jellyfin's volume mappings.** The owner has a standing instruction (comment in `compose/media-serve.yaml`) — `${SHARE_DIRECTORY}:/data/movies:ro` is intentional even though it looks misnamed. Three things are calibrated to that exact path: every Jellyfin library path, the \*arr `mapFrom`/`mapTo` mappings, and playlist-generator's `LOCAL_PATH_PREFIX`/`JELLYFIN_PATH_PREFIX` pair. `docs/decisions/0016-jellyfin-paths-are-load-bearing.md`.
- **`.env` holds two distinct concerns.** Variables consumed by the compose files (paths, domain, Cloudflare token, qBittorrent/slskd creds) _and_ `API_KEY_*` tokens used only by `scripts/`. When you add a script that needs a new key, document it in both `.env.example` and `AGENTS.md`'s env list.
- **Folder name casing matters.** The compose file expects lowercase subfolders under `${SHARE_DIRECTORY}` (`movies`, `series`, `music`, `downloads`, `books`, `nextcloud-data`). The README's old `Movies/Series/Music` casing is stale — trust the compose file.
- **Update path: `diun` notifies, a human applies. Watchtower is gone (2026-09-02).** Nothing in this stack can stop, remove or create a container any more. `diun` reads `diun/manifest.yml` — **generated** from the compose model by `scripts/emit_diun_manifest.py`, so run `make diun-manifest` and commit it after adding a service or `make check` fails — and watches each image's _repository_, which is what lets it report updates for the **pinned** `jellyfin` and `qbittorrent` tags that Watchtower structurally could not (it compared against the tag a container was started from). It pushes to `nas-alerts` at 04:10 and has **no route to the Docker API at all**. Applying is `docker compose pull <svc> && docker compose up -d <svc>`, or `make pull-jellyfin` / `make update-qbittorrent`. `dockerproxy` remains the only container touching `/var/run/docker.sock` and is now narrowed to `CONTAINERS`/`POST`/`PING`/`VERSION` — `IMAGES`/`NETWORKS`/`DELETE`/`INFO` existed only for Watchtower's recreate flow, the non-atomic one that logged `Failed=1` and left **no container at all** (qbittorrent, 13h, 2026-09-01), so dropping them removes the capability that caused the incident rather than an unused grant. `autoheal` is the proxy's only client; verified by canary restart, with `/images/json`, `/networks`, `/info` and `/exec` all returning 403. **Do not add a `com.centurylinklabs.watchtower.*` label** — `make check` rejects one. `scripts/stack_watchdog.py` (cron `*/5`) still alerts when a compose-defined service has no container at all, because a failed `docker compose up -d` can leave one. See `docs/decisions/0024-*.md` and `0025-*.md`.
- **`rootpage/dist/` is bind-mounted read-only into SWAG.** Editing source under `rootpage/src/` requires a `pnpm run build` before SWAG sees the change.
- **`docker-compose.yml.backup.*`** is a historical snapshot, not an active file. Don't edit it. The pre-split `docker-compose.yml` itself is likewise gone — recover it from git history (`git show a4beac9^:docker-compose.yml`) rather than looking for it on disk.
- **qBittorrent could not shut down gracefully — it was missing `CAP_KILL` (fixed 2026-09-01).** The recurring "qbit crashes and won't come back" cycle was one root cause with several symptoms. s6-overlay runs as root and signals `qbittorrent-nox`, which runs as `abc` (uid 1000); signalling across a uid boundary needs `CAP_KILL`, and `cap_drop: ALL` had removed it. Every SIGTERM was refused with `EPERM`, so Docker waited out the whole `stop_grace_period` and then SIGKILLed — measured 120.3s and no clean shutdown, versus 6.0s with `CAP_KILL`. **Correcting the old note here: this WAS a permissions problem** — a Linux capability one, not file ownership. Do not remove `KILL` from `cap_add`. Because every stop was a hard kill, qbit orphaned its `lockfile` and `ipc-socket` every time; with `CAP_KILL` it removes both itself, so the stale-lock path is now the exception rather than the rule. The tell for the s6 tight loop, if it ever recurs, is rapidly incrementing PIDs in `qbittorrent.log` while the container reports "Up (unhealthy)". Two backstops remain: `stop_grace_period: 120s` (now generous headroom, not a timeout that gets hit) and the custom-init script `qbittorrent/custom-cont-init.d/01-clear-stale-lockfile.sh`, which since 2026-09-01 **proves staleness before deleting** (0-byte pre-5.2.0 file, hostname mismatch, or dead PID) rather than unconditionally `rm -f`-ing. Do not reintroduce an unconditional delete. Also note the image is now **pinned** (`5.2.3_v2.0.14-ls473`, floor ≥5.2.2 for upstream #24357). Updates are a manual tag bump via `make update-qbittorrent`; watchtower — whose non-atomic stop→remove→create left qbit deleted with no replacement for 13h on 2026-09-01 — was retired entirely on 2026-09-02 (ADR-0025), and `diun` now reports new tags despite the pin (ADR-0024). Full writeup: `docs/qbittorrent-crash-fix.md`.
- **qui is a UI _over_ qBittorrent, not a replacement client.** `qui` (autobrr/qui) has no BitTorrent engine; it manages the existing qBittorrent daemon over the WebUI API at `qbittorrent:8080` and is published at `qui.4eva.me`. qBittorrent's own WebUI is retired as a _public_ surface, but its `127.0.0.1:8080:8080` loopback publish (now on the qbittorrent block itself, since the VPN was removed) **must stay** — `qbittorrent_settings_enforce.py`, `qbittorrent_stalled_kickstart.py`, and `media_ops_status.py` reach it at `localhost:8080` via qbit's localhost auth-bypass. qui connects from nas-network (not loopback), so it needs the real `QBITTORRENT_USER`/`QBITTORRENT_PASS`, entered once in qui's UI when adding the instance. **Deploy gotcha:** qui is NOT a linuxserver image and has no root init to chown `/config` — it runs directly as `${PUID}:${PGID}` and writes `config.toml`/`qui.db` itself. If Docker auto-creates `${CONFIG_DIRECTORY}/qui` as root on first `up`, qui crash-loops on `permission denied`. The host dir must be owned by `${PUID}:${PGID}` before starting (`mkdir -p ${CONFIG_DIRECTORY}/qui && chown ${PUID}:${PGID} ${CONFIG_DIRECTORY}/qui`). The public route is the manually-enabled SWAG preset `qui.subdomain.conf` (container name `qui`, port 7476); qBittorrent's own `qbittorrent.subdomain.conf` was disabled (`.disabled`) to retire its public WebUI.
- **`autoheal` is running again as of 2026-09-01, and it restarts `qbittorrent` and `slskd`.** It had been stopped since 2026-07-29 — collateral from a bare `docker compose stop`, not a decision about autoheal (its whole log was startup banners; it had never restarted anything). Practical consequence if you are cycling qbittorrent by hand: **a container going unhealthy will now be restarted out from under you within ~30s**, so an unexplained restart during testing is probably autoheal, not a crash. `docker logs autoheal` says so explicitly. Its two timeouts were wrong and are now `AUTOHEAL_DEFAULT_STOP_TIMEOUT=150` / `CURL_TIMEOUT=180`; the rule is stop-timeout ≥ the longest `stop_grace_period` in the stack, and curl timeout > that, or the restart call is cut off mid-stop, logged as failed, and re-issued on top of the one still in flight. To silence it for a service temporarily, remove the `autoheal=true` label rather than stopping the container — a stopped autoheal is invisible, which is how it went unnoticed for a month.
- **Cleanuparr is armed as of 2026-09-01, and three of its modules must stay off.** It is a deletion engine wired to qBittorrent and to Sonarr/Radarr; `dryRun` is `false`. Armed: Malware Blocker (local blacklist at `${CONFIG_DIRECTORY}/cleanuparr/blacklist.txt` — deliberately a file, not a URL), Queue Cleaner (failed-import 3 strikes, metadata 6, stall 12, slow 24, all bounded to 0–99% completion so a _completed_ torrent can never be struck as "slow"), and Download Cleaner (hourly, one seeding rule at qBittorrent's own 0.6 ratio / 34 h goals). **Off on purpose: Unlinked Downloads, Orphaned Files, Dead Torrents, Seeker, Blacklist Sync.** Do not enable them casually. `Unlinked` looks safe now that hardlinks work (commit `13dbdb9`) but the pre-restructure backlog is still `nlink=1` (425 files vs 1 hardlinked), so it would flag the whole download tree; `Dead Torrents` was tried in dry-run and rejected because "no seeders" means _no other seeder_, which is true of 25 of 59 completed torrents here — it struck Friends, Fargo and Planet Earth III, all healthy and mid-goal. **Lidarr must never be enabled in any Cleanuparr module**, and `failedImport.skipIfNotFoundInClient` must stay `true`: Lidarr's only client is slskd, which Cleanuparr cannot see, and that flag is what stops it striking a queue it has no view of. Also note **Sonarr/Radarr cannot tag torrents at all** (no tag field exists on their qBittorrent client) and the post-import category is empty on purpose — with `auto_tmm=true` a category change physically relocates the data. Full reasoning: `docs/cleanuparr-configuration.md`.
- **Never drive autoheal (or any auto-restart) off slskd's Soulseek login state.** slskd's web server can be up while its Soulseek login is dead. It is tempting to make the healthcheck probe `isLoggedIn` so a logged-out slskd gets restarted — that creates a permanent restart spiral. The login handshake times out after a hardcoded 5000ms when slsknet still holds a stale session for the username (a "ghost session" after a fast restart); a restart re-presents the same username and re-collides with the ghost, so it never recovers (32→64→128s backoff, container shows "Up N minutes" forever). The **only** cure is to leave slskd DOWN 15–30 min so slsknet reaps the session, then cold-start (`docker compose up -d slskd`). So slskd's healthcheck is deliberately **Soulseek-independent** (web-UI spider) and `autoheal=true` only restarts it if the web server itself dies. Login state is watched **alert-only** by `scripts/slskd_login_watch.py` (cron `*/15`), which never restarts. Don't reintroduce a login-aware healthcheck on the autoheal path.
- **Deletions in Sonarr/Radarr reach Jellyfin only because of a per-event toggle, and every delete-shaped one was off until 2026-09-02.** `mapFrom`/`mapTo` on the MediaBrowser (Jellyfin) connection decides _where_ a library-update call points; the `onXxx` toggles decide _whether_ a call is made at all. The path mapping was fixed 2026-09-01, which made imports work and hid the fact that deletes still sent nothing. Sonarr's `onSeriesDelete` and Radarr's `onMovieDelete` were `False` (with `supportsOnSeriesDelete: True` — the capability was there, unticked), so removing a series deleted the files and left Jellyfin holding a series plus episodes pointing at a dead path. **`onEpisodeFileDelete`/`onMovieFileDelete` being `True` does not cover this:** `DELETE /api/v3/series/N?deleteFiles=true` removes the folder in a single `RecycleBinProvider` operation and raises only `SeriesDeletedEvent`, so with the series-level toggle off `NotificationService` is never entered and the debug log shows **no dispatch line of any kind**. Both are now `True`. **Lidarr's `onArtistDelete`/`onAlbumDelete` are deliberately left `False`** — its MediaBrowser connection still exposes no `mapFrom`/`mapTo` fields, so enabling them would only send unmapped `/music/...` paths that Jellyfin drops while still answering `204`; deletion there stays the job of `scripts/lidarr_jellyfin_bridge.py` (cron `2-59/5`). Two traps when editing these over the API: `GET /notification` **masks `apiKey` as `**\*\*\***\*`**, so write the real key back into the field before the `PUT`(it is`API_KEY_JELLYFIN_ARR`, the `arr-integrations`key — _not_`API_KEY_JELLYFIN`, which is Jellyseerr's), and confirm the result in the DB rather than by re-`GET`ting (which re-masks); and `.docker-config/*/[app].db`is **WAL-mode**, so copying only the`.db`without`-wal`/`-shm`reads back stale values and will show a just-saved`1`as`0`. Verification is a three-line chain, and the \*arr Test button is not part of it (it returns `200` while only exercising an Emby _notify_ API Jellyfin does not implement): `MediaBrowser|Scheduling library update for series N` → `MediaBrowserProxy| … [POST] http://jellyfin:8096/Library/Media/Updated: 204.NoContent` in `sonarr.debug.txt`, then ~60–70 s later `LibraryManager: Removing item, Type: "Series", Name: …` in the Jellyfin log — that last line names the item, unlike the bare `LibraryMonitor … will be refreshed` line, which does not attribute the refresh. Safe live test without deleting real media: add a series with `monitor:none` and no search, then `DELETE` it with `deleteFiles=false&addImportListExclusion=false` — fires the real event, creates no folder, leaves no exclusion. Background: `docs/jellyfin-playback-audit.md` §4.1.
- **A wrongly-matched series hides media that looks perfectly fine in Sonarr and on disk.** Jellyfin had identified `/data/movies/series/3%` as **"3 Body Problem"** (`Tvdb 411959`/`tt13016388`), which has no season 4 — so the six real `3% - S04E01…E06` files Sonarr had imported were **never added to Jellyfin at all**, and the `Season 4` item was re-removed on every library refresh (`SeriesMetadataService: Removing virtual season 4`). Re-identified 2026-09-02 to the correct `Tvdb 250749`/`tt4922804`/`Tmdb 68467`; all 32 episodes on disk are now present. The lesson for auditing: a ghost sweep that walks **Jellyfin item → disk** (how the stale Ultraman entries were found) cannot see this failure, because it is the opposite direction — files on disk with no Jellyfin item. Check both ways; `Recursive=true&IncludeItemTypes=Episode&Fields=Path` compared against a walk of `${SHARE_DIRECTORY}/series` is enough, and Sonarr's own `tvdbId` is the authority for what a folder should have matched to.
